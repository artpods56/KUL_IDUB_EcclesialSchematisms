# Work packet 03: Safe migration 0020 downgrade

- **Status:** Not implemented at the interruption checkpoint
- **Parent slice:** [Slice 9](../09-system-catalog-and-runtime.md)
- **Outcome:** Migration 0020 refuses to discard explicit selection state that
  migration 0019 cannot represent

## Problem

Migration 0020 adds exact family selections, lifecycle, generation, and publisher
state. Its downgrade currently refuses only when System releases exist, then
drops `plugin_release_selections`. A Workspace family rolled back to an older
revision or marked deprecated/withdrawn would silently return to 0019's implicit
maximum-revision behavior.

Downgrade safety belongs in the migration preflight. Do not teach current
application services to emulate an old schema.

## Required invariants

1. Existing System-release provenance continues to block downgrade.
2. An empty database may downgrade.
3. Workspace releases that existed before the 0020 upgrade and whose untouched
   selections were generated by `_backfill_selections()` may downgrade.
4. Every other Workspace selection state fails closed before any table, index,
   constraint, or column is dropped.
5. A failed downgrade leaves schema and data byte-for-byte unchanged.

## Losslessly representable Workspace state

A family is representable by 0019 only when all of these are true:

- exactly one selection exists for the family;
- it selects the family's highest retained revision and matching release ID;
- lifecycle is `published`;
- generation is `1`;
- `updated_by_actor` is `migration:0020`.

Also reject a release family with no selection row. This can happen when a new
release was staged without promotion; 0019 would incorrectly treat its maximum
revision as current.

The strict generation/actor rule intentionally rejects post-migration selection
activity even when the pointer later returns to the maximum revision. That audit
and concurrency state cannot be reconstructed after downgrade and re-upgrade.

## Current partial state

`infra/db/migrations/versions/0020_plugin_release_selections.py::downgrade()`
currently:

1. counts System releases;
2. raises if any exist;
3. unconditionally drops both selection indexes and the selection table;
4. removes System publisher provenance from `plugin_releases`.

No Workspace selection preflight had landed when the agent was stopped.

## Implementation steps

1. Before any destructive DDL, query every Workspace release family and its
   selection state with portable SQLAlchemy Core statements.
2. Detect missing, extra, non-maximum, lifecycle-mutated, generation-mutated, or
   actor-mutated selections.
3. Raise one contextual `RuntimeError` explaining that 0019 cannot represent the
   state. Include the family slug and Workspace ID when possible [R42: Errors
   Carry Context].
4. Only execute the existing drop operations after both System and Workspace
   preflights pass.
5. Keep the existing clean upgrade/backfill/downgrade round trip green.

## Behavioral acceptance tests

Extend `test_migrations.py` with separate cases proving rejection for:

- a selection pointing to an older retained revision;
- `deprecated` and `withdrawn` lifecycle values;
- generation greater than one, even if the selected revision is maximum;
- a non-migration actor;
- a family with releases but no selection;
- existing System releases, preserving the current guard.

For every rejected case, assert the selection table, rows, indexes, publisher
column, and check constraint still exist. Keep the existing untouched-backfill
downgrade test as the positive case.

## Implementation evidence

Files changed (relative to HEAD):

- `infra/db/migrations/versions/0020_plugin_release_selections.py` (new) — `downgrade()` now calls `_require_workspace_selections_representable(connection)` after the existing System-release guard and before any `op.drop_index` or other DDL. The preflight refuses the downgrade with one contextual `RuntimeError` (naming the offending `slug` and workspace) whenever any Workspace family's selection is missing or extra, points at a non-maximum retained revision, has a lifecycle other than `published`, carries a generation above the backfill's 1, or was written by an actor other than `migration:0020`. A refused downgrade leaves the schema byte-for-byte unchanged because no DDL has run yet.
- `tests/unit/persistence/test_migrations.py` (modified) — 5 new tests plus shared helpers (`_selection_snapshot`, `_release_snapshot`, `_assert_0020_downgrade_refused_leaves_schema_unchanged`): `test_0020_downgrade_refuses_selection_pointing_at_older_retained_revision`, `test_0020_downgrade_refuses_mutated_selection_lifecycle` (parametrized over `deprecated`/`withdrawn`), `test_0020_downgrade_refuses_generation_above_backfill`, `test_0020_downgrade_refuses_non_migration_selection_actor`, `test_0020_downgrade_refuses_family_without_selection`. Each test mutates the backfilled state after upgrading to `head`, downgrades to `0019_scoped_plugin_releases`, and asserts the refusal message plus an unchanged schema snapshot (columns, `PRAGMA index_list`, and `sqlite_master` check-constraint state).
